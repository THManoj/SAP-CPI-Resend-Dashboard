1. EXECUTIVE OVERVIEW: WHAT DOES "RETRIGGER" MEAN IN THIS APPLICATION?
================================================================================
In standard SAP Cloud Integration (CPI / BTP), there is no native "Resend" button 
like there was in legacy SAP Process Orchestration (PO / PI PIMON). 

When a message fails in SAP CPI:
1. The failed message execution is permanently logged in the Message Processing 
   Log (MPL) with status "FAILED".
2. The payload that caused the failure (or was attached during the flow) is 
   stored as an MPL Attachment (e.g., "Payload_Snapshot").
3. To "retrigger" or "replay" that failed message, our application:
   - Fetches the authentic payload from the failed message's attachment directly 
     in volatile RAM.
   - Automatically determines the exact SAP CPI runtime HTTP endpoint for that 
     integration flow.
   - Injects SAP PO lineage headers (SAP_ParentMessageId, SAP_MplCorrelationId) 
     so audit trails remain intact.
   - Executes an authenticated HTTP POST request to the SAP CPI integration 
     flow runtime endpoint.
   - SAP CPI processes this retrigger as a brand-new transaction linked 
     to the parent message, creating a new MPL log.
   - The UI moves the message out of "Failed" into a dedicated "Resent" column.

6. DYNAMIC ENDPOINT RESOLUTION (How Target iFlow URL is Discovered)
================================================================================
Method: `resolveIflowEndpoint(String iflowName, String token)` (Lines 390-433)

How does the backend know WHERE to send the message?
1. The backend inspects `tenantUrl`:
   e.g.: https://b65f2da8trial.it-cpitrial03.cfapps.ap21.hana.ondemand.com
2. In SAP BTP Cloud Foundry, the runtime integration engine endpoint format is:
   https://<subdomain>.it-cpi001-rt.cfapps.<region>.hana.ondemand.com/http/<iflowName>
   or
   https://<tenant-url>/http/<iflowName>
3. The method dynamically transforms the tenant URL into the runtime base URL:
   `rtBase = tenantUrl + "/http/" + iflowName;`
4. This ensures that the destination URL is never hardcoded and is completely 
   hidden from the UI for security.

7. LINEAGE & AUDIT HEADERS (Preserving Parent Tracking)
================================================================================
When a message is resent, it enters SAP CPI as a new transaction. 
How do we know which failed message it came from?

We inject standard SAP PO enterprise headers into the retrigger request:
- `SAP_ParentMessageId`: Contains the Message ID of the failed execution.
- `SAP_OriginalMessageId`: Preserves the initial root transaction ID.
- `SAP_MplCorrelationId`: Preserves the correlation ID so both logs can be 
  queried under the same correlation ID in SAP BTP Cockpit.
- `SAP_ResendAttempt`: Marks this execution as attempt #1.
- `SAP_SourceSystem`: Identifies that the replay originated from this monitor.

In the target iFlow in SAP CPI, you can read `${header.SAP_ParentMessageId}` 
in Groovy or Content Modifier to log the parent link!

8. ZERO-DISK VOLATILE MEMORY HANDLING (Strict RAM-Only Lifecycle)
================================================================================
Per the architecture specification (`plan.pdf`):
1. Payloads are NEVER written to a local `.txt`, `.json`, `.xml`, SQLite, or 
   temporary scratch file on disk.
2. The payload bytes are read directly from the SAP CPI OData attachment stream 
   into an in-memory `String`.
3. The `String` is passed as the body of Spring's `HttpEntity`.
4. Right after `rest.postForEntity(...)` executes, the reference is set to `null`:
   `payloadToSend = null;`
5. The Java Garbage Collector immediately reclaims the RAM.

9. WHAT HAPPENS INSIDE SAP CLOUD INTEGRATION WHEN RETRIGGERED?
================================================================================
When the HTTP POST arrives at `https://.../http/resend-testing`:
1. The SAP CPI HTTP Inbound Adapter receives the call.
2. SAP CPI verifies the OAuth Bearer token (`rtToken`).
3. SAP CPI generates a brand new `MessageGuid` and starts a new Message 
   Processing Log (MPL).
4. Because our headers contain `SAP_MplCorrelationId`, SAP CPI assigns the SAME 
   correlation ID to this new log.
5. The iFlow steps execute with the replayed payload.
6. In the SAP BTP Cockpit, you will see two messages sharing the same Correlation ID:
   - Message 1: The original message (Status: FAILED).
   - Message 2: The retriggered message (Status: COMPLETED or PROCESSING).
7. In our dashboard:
   - Message 1 is categorized under the "🔄 Resent" column.
   - Message 2 appears in the log table as the new execution.

10. SUMMARY FAQ
================================================================================
Q: Can a message without an attachment be resent?
A: No. Both the frontend button and the backend service strictly reject resending 
   if no valid payload attachment exists, to avoid firing blank requests into iFlows.

Q: Can successful messages be resent?
A: No. Resend is disabled for successful messages.

Q: Can a resent message be resent a second time?
A: No. Once replayed, the message transitions to the Resent state and the replay 
   button is disabled to prevent duplicate processing.

Q: Where are resent comments stored?
A: In an in-memory thread-safe `ConcurrentHashMap` in the backend service and in 
   the user's browser session state, maintaining zero disk persistence.
